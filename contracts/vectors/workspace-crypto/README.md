# `workspace-crypto` golden vectors

The **client-held** cryptographic formats of Koru Cloud, pinned as data.
Desktop, Android and iOS each implement these, and the tri-platform pass over
this directory is Plan 10.7's GA gate (D42).

Generated by `crates/koru-workspace-crypto`. To regenerate after a deliberate
format change:

```
KORU_UPDATE_WORKSPACE_CRYPTO_VECTORS=1 cargo test -p koru-workspace-crypto
```

The default suite asserts these files are current and, separately, **verifies
them** — it decodes every case from the published bytes and checks it behaves as
the file says. Editing a vector by hand fails the second test, which is the
point of having it.

| File | Format | What it pins |
| --- | --- | --- |
| [`wek-grant-v1.json`](wek-grant-v1.json) | `WekGrantV1` | Layer 1. HPKE Base grants under both KEMs, the customer-managed workspace with no Koru recovery grant, and the refusals |
| [`content-object-v1.json`](content-object-v1.json) | `ContentObjectV1` | Layer 2. Blob objects, the chunk-boundary cases, and the D40 plaintext-length derivation |
| [`recovery-checkpoint-v1.json`](recovery-checkpoint-v1.json) | `WorkspaceRecoveryCheckpointV1` | The approved `WorkspaceRecoveryBootstrapV1` field table, sealed |
| [`blob-identity-v1.json`](blob-identity-v1.json) | `CloudObjectId`, `BlobMappingRecordV1` | Keyed BLAKE3 object identity, and the encrypted `BlobHash` mapping |

The format document these implement is
[`workspace-crypto-formats-v1.md`](../../../docs/cloud-platform/contracts/workspace-crypto-formats-v1.md), and
the reasoning is [ADR-337](../../../docs/decisions/ADR-326-350.md).

## How to apply them

Every file has a `cases` array. Each case carries `result`:

- **`valid`** — the operation must succeed and produce exactly what `expect`
  (or `wek`, or `plaintext_len`) states.
- **`invalid`** — the operation must **fail**, with the stable code in `error`.
  An implementation that produces plaintext for one of these has a
  vulnerability, not a difference of opinion.

`stage` says how far a case gets before it must fail: `parse` means the
envelope must be refused without a key; `signature` means it parses and the
Ed25519 check refuses it. A case with no `stage` is refused during the open.

All byte fields are lowercase hex. Ids are hyphenated lowercase UUIDs.

**The writer policy is data too.** `wek-grant-v1.json`'s `suites[]` carries a
`writable_for` list per suite. A suite absent from a recipient's list is
readable and **must not be selectable for a new write** to that recipient — that
is how "a deprecated suite is unselectable for new writes" is expressed here,
because a refusal to write has no ciphertext to publish.

## Most of these are failures, on purpose (D91)

A vector suite that only proves two implementations agree on the happy path
proves that they will also agree on accepting a forgery. The required failing
cases — wrong workspace, wrong recipient, a modified `wek_version`, cross-region
recovery, truncated, extended and reordered chunks, malformed lengths that must
not overflow a parser, unknown suites failing closed, and a customer-managed
workspace having no Koru grant — are all here, and each is named after what it
attacks.

**Two refusals that read alike and are not.** A byte added to or removed from
the *final* chunk still leaves an arithmetically valid ciphertext length, so the
AEAD tag is what refuses it. Truncation at a *chunk boundary* is refused by the
framing, before any key is used. An implementation that only had the first would
still pass a happy-path interop suite and would accept a truncated file.

## Why `content-object-v1.json` is 170 KB

A single chunk is 16 KiB, which is 33 KB of hex. Ciphertext is published where
an implementation could plausibly be wrong — the empty message, a single byte,
and both sides of the first chunk boundary, which is where a wrong final-chunk
rule or a wrong chunk counter shows. Every other length, up to and past the
10 GiB blob ceiling, is pinned in the `plaintext_length_derivation` table, where
no bytes are needed to state the answer.

## Upstream conformance for the chunked layer

`ContentCipherSuiteV1` is
[c2sp.org/chunked-encryption](https://c2sp.org/chunked-encryption) instantiated
as Cobblestone-256. Its conformance suite is **Project Wycheproof's**
`c2sp_chunked_encryption_aes_256_gcm` vectors — 35 cases written by somebody who
did not write our implementation — vendored at
`crates/koru-workspace-crypto/vectors/wycheproof/` and run by the default suite.
The files here pin Koru's framing *on top of* that, and deliberately do not
restate it.

## What is not here

- **Segments and snapshots** share `ContentObjectV1` with blob objects and
  differ only in the bound `purpose`. They are Cloud-written and no client ever
  encodes one, so they carry no client-held vector.
- **The account-metadata envelope** is server-only: no client holds the key and
  no client implements the format. Its vectors are in
  [`../account-metadata-envelope/`](../account-metadata-envelope/).
