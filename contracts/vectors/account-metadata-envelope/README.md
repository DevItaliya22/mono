# `account-metadata-envelope` golden vectors

The **server-only** account-metadata envelope (D56/D57/D59). No client holds
this key and no client implements this format, so — unlike
[`../workspace-crypto/`](../workspace-crypto/) — this is not a tri-platform
suite. It is verified by the regional account service, its KMS adapter, the
rotation job, and backup/restore.

Generated by `crates/koru-workspace-crypto`; regenerate with

```
KORU_UPDATE_WORKSPACE_CRYPTO_VECTORS=1 cargo test -p koru-workspace-crypto
```

## What it pins, and what it deliberately does not

It pins the **envelope**: the layout, the fields bound into the key derivation,
the key id and version, the purpose separation, and the rotation behaviour —
over an **opaque plaintext**.

It does not pin the tombstone's field table. Which entries a purged account
record carries is regional account-domain behaviour and belongs with its domain
(Plan 3.2). A cryptography crate with an opinion about account-domain fields
would put the tombstone's shape under a plan that never reads it.

## The hierarchy (D59)

```text
regional metadata KEK  (KMS, one per region, symmetric)
  └── wraps ──►  per-account metadata key  (RANDOM, one per account)
                   └── encrypts ──►  every account-metadata record
```

The per-account key is **random**, never `KDF(regional_key, account_id)`. A
derived key can be recomputed from public inputs, so destroying it would destroy
nothing and individual crypto-erasure would be a fiction.

The wrapped key is stored **once per account**. An envelope references it by
account, key id and version and never contains it — if every envelope carried a
copy, destroying "the" wrapped key would erase nothing.

**An envelope does not name the KEK.** Which KEK wraps the account key is a fact
about the wrapped-key record and changes on rotation; a copy in every envelope
would be stale the moment it rotated.

## What crypto-erasure covers, stated honestly (D90)

Destroying the wrapped per-account metadata key renders unrecoverable
**ciphertext whose only remaining decryption path is that key**. That is a real
and useful property, and it is not the same sentence as "deletion erases their
data". It is defeated by plaintext in logs, a search index over the plaintext,
caches, analytics events carrying the values, or **backups of the unwrapped
key**. Those are operational controls; no format decision here supplies them.

The `destroying the wrapped key renders the envelope unrecoverable` case
demonstrates the cryptographic half: with the wrapped key gone, the nearest key
an operator still holds is the KEK itself, and it opens nothing.

## Rotation

Rotating the **KEK** rewraps one record per account, touches no envelope, and
leaves no stale field behind. Rotating the **account key** re-encrypts every
envelope — the same operation as crypto-erasure with a replacement, and why it
is spelled out rather than left implicit.
